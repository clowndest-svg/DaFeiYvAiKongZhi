# QQ 掉线恢复重做（2026-11-02 定稿）

起因：今天 07:21 电脑睡眠导致 NapCat 掉线，09:59 唤醒后旧的"自动恢复"每 20 分钟杀一次 NapCat 重启登录，
**22 次全部无效**（重启后必须人扫码）；16:30 主人点「重新生成」准备扫码，16:33 自动恢复又杀了一次，
16:36 二维码被换新 → 他扫的那张作废。这就是"老掉线 + 二维码有时登不进去"。

## 一、实测到的事实（不是推测）

| 事实 | 怎么量出来的 |
|---|---|
| NapCat 反向 ws **自己每 3 秒重连** | `napcat/config/onebot11_<机器人小号>.json` 里 `reconnectInterval: 3000` |
| 这台机器是 **S3 传统睡眠**，没有 S0 现代待机 | `powercfg /a` → "待机 (S3)"，S0 在"没有"列表里 |
| 睡眠会让 QQ/Node 一起停 | Windows 电源诊断 11-02 09:59 记录"从睡眠恢复"；断连起点 07:21 |
| NapCat 侧也会主动关 ws | 16:28 日志只有 `NapCat 连接已断开`，我们没重启 |
| 启动器 `NapCatWinBootMain.exe` 注入成功后自己退出 | 三次轮换后 `accounts` 快照里它消失、QQ 还在 |
| 我们已有 `get_status` 通道 | `sendAction` 里 `get_status`/`get_login_info` 是不受身份闸门限制的白名单动作 |

## 二、GPT 交叉评审采纳了什么（逐条回源核实）

| 它的意见 | 核实结果 | 采纳 |
|---|---|---|
| 删掉"断满 30 分钟就重启活着的 QQ" | 实测 `reconnectInterval: 3000`：NapCat 本来 3 秒重试一次，我们重启只会踢掉登录态 | ✅ 删 |
| NapCat 有"账号静默离线但进程/WS/心跳都活着"的假活模型 | 无法验证我们的版本是否有此 bug，但 `get_status` 现成可用 | ✅ 加账号状态探测，且**不据此自动重启** |
| 二维码 mtime 只证明"文件被改过"，不能推断登录状态 | 对。措辞降级为"发现登录二维码（X 秒前）" | ✅ |
| 进程查询失败不能当成"进程不存在" | 对，`listOwned` 异常/超时会被误判成 0 → 会误启动 | ✅ 改三态 present/absent/**unknown**，且要连续两次确认 |
| 心跳间隔只能证明"监测中断"，不能认定"电脑睡了" | 对，长任务阻塞/挂起也会造成 gap | ✅ 原因字段写 `monitor_gap`，界面写"未确认" |
| 我们自己的监听故障也会表现为"连不回来" | 现在拒接只写日志不计数 | ✅ 加拒接计数与原因（bad token / origin / 通道停用） |
| S0 待机下"智能待机断网"等 | 这台是 S3，不适用；改成"AC 下不睡" | ⚠️ 按 S3 处理 |

## 三、定稿设计

### 信号（各自独立，互不推断，都带 observedAt）
- `transport`：反向 ws 是否连着（`clients.size > 0`）
- `account`：`get_status` 的 `data.online` / `data.good` → `online | offline | unknown`（连着时每 60 秒探一次；超时/字段缺失一律 unknown）
- `client`：QQ.exe 进程数 → `present | absent | unknown`（查询失败=unknown）
- `qr`：`napcat/cache/qrcode.png` 的 mtime → 只表述"发现登录二维码（X 秒前）"
- `rejected`：我们这侧拒掉的握手次数与最近原因

### 唯一的自动动作（定稿时收紧了）
**运行期间完全不自动碰进程**——不 kill、不 start。原因：QQ.exe 是多进程，而且这台机器上主人自己的
主号 QQ 也在跑，**没法可靠判断"还在的 QQ 进程是不是机器人小号那一个"**；在这种不确定性下自动杀/自动起
都可能把好端端的登录干掉。所以：

- transport 断、QQ 进程还在 → 只等（NapCat 实测 3 秒自己重连一次）。
- account=offline/unknown 而 transport 连着 → 界面说"通道连着，但账号状态未确认/离线"，**不重启**（重启解决不了登录）。
- 断够 10 分钟仍未恢复 → 只升级提示：界面 + 走已有的告警路径提醒主人"需要人工处理"。
- 人工动作保留三个按钮：「二维码过期？重新生成」「用机器人小号重新登录」「立刻停用 QQ 通道」。

只留一个窄口子——**开机自愈**：本进程启动后的头 3 分钟内、且从未连上过、且 `QQ.exe 数为 0（查询成功才算数，
失败=unknown 不动）`、且 NapCat 启动器不在 → 允许 `startNapCat()` 一次（它只启动、不 kill），每次进程生命周期最多一次。
覆盖"机器重启后 NapCat 没自启"这一种场景，其余情况交给人。

### 扫码操作锁
出现下列任一情况 → 挂起全部自动动作 15 分钟（可续期）：
发现 5 分钟内的新二维码；主人点过「重新生成」；主人点过「用机器人小号重新登录」。
界面明说：「我在等你扫码，这 15 分钟内我不会动 NapCat（还剩 X 分）」——这是对人的承诺，不谎称 NapCat 不会自己换码。

### 断连统计
kv `qq_outage_log`（JSON 数组，保留最近 200 条）：
`{startedAt, endedAt, minutes, cause, autoStarts, scanned, transportOnly}`
`cause ∈ napcat_closed | client_gone | our_restart | monitor_gap | unknown`；
`our_restart` 用进程启动时生成的 bootId 判定（我们重启过 = 断开时 bootId 变了）。
界面显示最近 7 天：断几次、累计多少分钟、平均多久恢复、最近一次原因；**没有记录就显示"无读数"**，不编。

### 电源（这台是 S3）
只在**接通电源**时禁止睡眠：`powercfg /change standby-timeout-ac 0`、`hibernate-timeout-ac 0`；电池设置一律不动。
改前把当前值读出来存进 kv 并写清回退命令；改后用 `powercfg /q SCHEME_CURRENT SUB_SLEEP STANDBYIDLE` 读回校验。
**合盖动作不改**（合盖不睡有放包里过热风险），文档明说"合上盖子仍会睡"。

## 四、验收判据（正反样本，都要跑变异）

1. 运行期任何信号组合都**不得**触发进程启动/停止（变异：把旧的 20 分钟或 30 分钟重启留着 → 红）。
2. 开机自愈只在"启动后 3 分钟内 + 从未连上 + QQ 进程查询成功且为 0 + 启动器不在"四条同时成立时启动一次（变异：去掉任一守卫 → 红）。
3. 进程查询抛错 = unknown，不得启动（变异：把异常吞成 0 → 红）。
3. transport 断 + QQ 进程还在时，无论等多久都不碰进程（变异：把"到点重启"留着 → 红）。
4. 扫码锁生效期间界面承诺"不会动 NapCat"，且 `/api/qq/qr/restart` 之外没有任何路径换码（变异：删锁 → 红）。
5. 开机自愈一个进程生命周期最多一次（变异：去掉 once 标记 → 红）。
6. `get_status` 超时/缺字段 → account=unknown，界面不得显示"在线"（变异：默认当 true → 红）。
7. outage 成对：只有 endedAt 存在才计入统计；未闭合的当前 outage 单独显示"进行中"。
8. `monitor_gap` 只在 tick 间隔 >3 分钟时记，且界面文案含"未确认"。
9. 电源：改前值入 kv、改后读回等于 0、电池项**没变**（三条都要断言）。
10. 状态接口三态文案与 `qqRecovery` 字段一致（静态判据钉字段名 + 真机看面板）。

## 五、爆炸半径

只动：`onebot.checkConnectionHealth`（重写为信号采集，运行期不碰进程）、`restartQqLogin`（只留给用户手动点，并挂扫码锁）、
`/api/status` 的 `qq.recovery`、控制台 QQ 面板与顶栏告警文案、`qq.autoRecover` 这个设置项整个删掉（默认值/归一化/勾选框一起删，
不留一个不再生效的开关骗人）、新增 `tests/qq-recovery.test.js`、系统电源 AC 项。
不影响：消息收发路径、语音会话、小红书/空间调度、身份闸门。
风险与消解：① 不再定时重启 → 真需要重启的场景变慢（消解：开机自愈仍会起一次 + 界面三个手动按钮 + 断够久直接提醒他要扫码）；
② 新增 `get_status` 轮询 → 每分钟一次轻量调用（消解：只在连着时发，超时即 unknown，失败不影响收发）；
③ 进程探测用 `execFileSync` 会阻塞事件循环（消解：只在开机自愈那一次调用，不进 30 秒心跳）；
④ 电源改动（消解：只改 AC、改前存 `data/power-before.json`、读回校验、`--revert` 可回退）。

## 六、执行结果（17:30 实测，不是计划）

**电源（第 4 条）实测和预想不一样**：这台机器 AC 下本来就不睡——`standby-timeout-ac=0`、`hibernate-timeout-ac=0`
（休眠项 GUID 用别名才读得到，按 GUID 读会报"设置不存在"）。真正开着的是两个**网卡/总线省电**：

| 项 | 改前（AC/DC） | 改后 AC | 说明 |
|---|---|---|---|
| PCI Express 链接状态电源管理 (ASPM) | 2 / 2 | **0** | 2 = 最大电源节省，是"链路掉网卡"的常见来源 |
| USB 选择性暂停 | 1 / 1 | **0** | 启用状态会挂起 USB 设备 |
| standby-timeout | 0 / 600 | 0（本来就是 0） | 电池仍是 10 分钟，没动 |
| hibernate-timeout | 0 / 10800 | 0（本来就是 0） | 电池 3 小时，没动 |

电池四项**一律没动**（拔电仍按原计划睡眠，避免亏电/过热）；合盖动作在这个电源方案里读不到（OEM 精简），
**合上盖子仍会睡**，那条由固件决定。原值存在 `data/power-before.json`，回退：`node tools/set-power.mjs --revert`。

**轮换的副作用（新发现，得记住）**：两次生产轮换后，NapCat 启动器进程都从进程清单里消失了
（11-01 的 17380、11-02 的 25016），并且 NapCat 随后写出新的登录二维码。也就是说
**我们重启小知，可能让他重扫一次码**。所以以后轮换要挑他没在扫码的时候，且能一次改对就一次改对。

**新逻辑上线后的真实快照**（17:27 轮换后 1 分钟，`/api/status` 的 `qq.recovery`）：

```
policy      运行期不自动重启 NapCat（它自己每 3 秒重连）…
bootStart   { started:false, reason:"QQ 进程还在，可能正在自己重连", qqState:"present", qqCount:20 }
scanLocked  true   ← 发现 17:26 生成的登录二维码，自动挂锁
outage      { startedAt:17:27:19, cause:"napcat_closed", endedAt:null }
account     { state:"unknown" }   rejected { count:0 }
告警条      [danger] QQ 断了 4 分钟，她在等你扫码——扫码这段时间她不会动 NapCat
```

开机自愈判过之后**没有动手**（QQ 进程还在），扫码锁挂上，断连记录开了没闭合的那条，
告警从旧版那句骗人的"她在自己试着恢复"换成了实话。

**判据**：`tests/qq-watchdog.test.js` 7 条 + `tests/qq-recovery.test.js` 4 条。三个变异各自打红：
探测失败当在线（MA）→「连回来时…」红；去掉 unknown 守卫（MB）→「unknown 绝不能当成没在跑」红；
去掉扫码锁（MC）→「发现新码却没挂扫码锁」红。全量 393 项 / 388 通过 / 0 失败 / 5 跳过；界面体检 30/30；
生产 PID 16280。

不影响：消息收发路径、语音会话、小红书/空间调度、身份闸门。
风险与消解：① 不再定时重启 → 真需要重启的场景变慢（消解：client=absent 仍会自动启动一次 + 界面一键"重新登录"）；
② 新增 `get_status` 轮询 → 每分钟一次轻量调用（消解：只在 transport 连着时发，超时即 unknown，失败不影响收发）；
③ 电源改动（消解：只改 AC、改前存值、可回退、读回校验）。
