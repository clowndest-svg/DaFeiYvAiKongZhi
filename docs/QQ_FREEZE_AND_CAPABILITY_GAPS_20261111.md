# 冻结 QQ 版本 + 聊天里「做不到」的归因（2026-11-11）

> 后续实施已补齐本文列出的聊天入口、截图、桌面工具和源码读改。本文保留当时诊断，现行能力与验收见 [主人聊天工具交付](OWNER_TOOLS_DELIVERY_20261111.md)。

起因：主人发现 SnowLuma 上游不再维护，担心「QQ 一升级，协议端没人适配，项目就瘫」；同时给出一段与她的聊天记录，
她反复说自己没有能碰电脑的口子。本文把**今天在这台机器上量到的事实**、**已经做的改动**、以及**聊天里那些「做不到」到底
是能力缺失还是配置挡住**分开写清楚，不把推测当结论。

腾讯云控随时会重下一个包，那个包现在也不在了。要真正冻结，必须让 QQ **放不进新版本**。

## 二、这次做了什么：`tools/freeze-qq-update.mjs`

在 `<QQ 安装目录>\versions` **这一层目录**加了一条 ACL 拒绝规则：

```
Everyone:(DENY)(WD,AD)     ← 只在本目录生效，没有 (OI)(CI) 继承标志
```

- `WD/AD` 对应 `CreateFiles` + `CreateDirectories`：QQ 既下不进 `<版本>.zip`，也解压不出 `<版本>/` 目录，**换装在物理上不可能**。
- 规则**不继承**：`9.9.28-46928/` 内部完全不受影响。
- 已有的 `config.json` / `setting.json` / `channel.json` 仍可写，所以 QQ 每小时 `clearReadyVersion` 照常成功，登录、收发、注入都不动。
- 登录态在 `%APPDATA%\QQ\auth`，与 `versions/` 无关；**全程没有结束任何 QQ 进程**（复核时 10 个 `QQ.exe` 仍在）。

### 命令

```bash
node tools/freeze-qq-update.mjs --show       # 只读：规则在不在、现役版本、待装包、readyVersion
node tools/freeze-qq-update.mjs --freeze     # 冻结（幂等；自检不过会自动撤回）
node tools/freeze-qq-update.mjs --unfreeze   # 放行（精确移除这一条规则，不改写原有 ACL）
node tools/freeze-qq-update.mjs --freeze --dir "<QQ 安装目录>"   # 注册表读不到时手动指定
```

### 本次执行结果（2026-11-11 10:08 UTC+8）

```
✓ 不能在 versions/ 新建文件
✓ 不能在 versions/ 新建目录
✓ 已存在的 config.json 类文件仍可写
✓ 现役版本目录仍可读
✓ 已冻结：新增拒绝规则
```

- 写入前备份（ACL 的 SDDL + 三个 json 原文）：`data/qq-update-freeze/before-2026-11-11T02-07-55.json`
  和 `before-2026-11-11T02-18-40.json`（第二份是回退实测后重新冻结时生成的）。
- 状态文件：`data/qq-update-freeze/state.json`（记录 frozenAt、QQ 版本、备份路径）。
- 冻结时 QQ 版本：`9.9.28-46928`，`readyVersion` 空，无待装包。
- **回退不是纸面承诺**：实际跑过 `--unfreeze`（`--show` 确认规则消失、`versions/` 可新建文件）→ 再 `--freeze`（四项自检重过、规则恢复），
  最终状态为「已生效」。全程未重启 QQ、未重新扫码。
- 判据：`tests/qq-update-freeze.test.js` 8 条全过（含「规则不继承」「show 不改 ACL」「按 SID 翻译识别」「读不到配置要报 error」）。

### 说清楚做不到的部分

- 拦**不住**：人手动运行完整安装包（`QQSetup.exe`）覆盖安装、换安装目录、或腾讯服务端下发「最低可用版本」强制策略。
  这些不属于「自动热更新」，需要人决定。
- 冻结后 QQ 仍会每小时查更新、仍会写 `updater.log`，只是**放不进新版本包**；日志继续写「无需更新」属正常。
- 项目原有的 `checkNapcatVersions` 每 12 小时对账、`qq_upgraded` 事件与断线横幅**继续保持**，作为第二道观察：
  万一冻结被绕过并真的换装了，能立刻看到，而不是等她连不上才发现。
- 真要升级 QQ：`--unfreeze` → 升级 → 核对 SnowLuma/NapCat 与新版 QQ 的组合 → 再 `--freeze`。

## 三、SnowLuma 停更：风险与本机还剩下的牌

公开讨论显示上游仓库约两天前由公开转为私有/删除（法律风险），本项目**不再有官方渠道拿新版本**。
这不是猜测出来的兼容性结论，只是「没有后续适配」这一事实；`v2.4.0` 现在能用，不等于未来 QQ 换了还能用。

### 风险与缓解

1. **QQ 换版本 → hook 失效且上游不会再修**：本次冻结把这条路堵上；真换版本时按上面的顺序人工验收。
2. **长期停在 2026-03 的 QQ 9.9.28**：腾讯可能停止给旧版下发消息或强制最低版本。冻结是「现在不坏」的取舍，
   不是永久免疫；建议每月看一眼 `updater.log` 与 QQ 面板是否出现「版本过旧」提示。
3. **别把回退弄成数据事故**：回退只改 `BIZHI_QQ_PROVIDER` 和接入端，**绝不能用迁移前数据库覆盖当前库**（会丢新聊天、
   记忆和费用记录）。这一条 `docs/qq-provider-migration.md` 已写明。
4. **离线包要留两份**：`data/` 在 `.gitignore` 里、也不在自动备份范围内。建议把 `.verified.zip` 和 `snowluma/config/`
   单独拷到另一块盘/移动硬盘，否则重装系统时这套「唯一的 v2.4.0」会一起没。

## 四、聊天记录里「做不到」的归因（这才是重点）

她说的话大多**准确且诚实**——`config/persona.md` 与 `src/prompt.js` 本来就要求「不撒谎、做不到就承认、
解释一次只说一遍」。但造成「很多事做不到」的原因分三类，混在一起看会误判成「功能都没做」。

### 4.1 其实功能在，被配置/路由挡住了（优先处理，多数不用写代码）

`data/logs/app-2026-11-10.log` / `app-2026-11-11.log` 的实证：

| 日志现象 | 影响 |
| --- | --- |
| `余额 4.97 / 4.95 元低于 5 元：暂停语音和自动运营` | 熔断连续挡下：**周记、睡前反思、自动发说说、空间自动回复、X 自动互动、小红书自动互动、小红书自发笔记、抖音刷视频**。阈值是设置项 `cost.lowBalanceCny = 5`（`src/budget.js:15`），可改；更硬的 `stopBalanceCny = 1.5` |
| `POST /api/douyin/browse` → 409「请先读取我的作品完成账号绑定」 | 抖音**没绑定账号**，所以「刷不了抖音」不是能力缺失 |
| `msglist 读取失败…QQ 空间 Cookie 可能失效或触发风控`，11-10 到 11-11 反复出现 | 空间走 `feeds3` 降级，降级后仍能读到 1 条说说；需要重新复制完整 Cookie |
| `小红书要求安全验证或提示账号限制，已停止动作` | 平台风控，程序按设计停 6 小时，不是代码坏了 |
| `POST /api/balance` → 409「这个操作正在处理中」×4 | 低危并发，但会让人以为界面卡死 |

对照 README 第 2 节：X（推特）和抖音**模块本来就有**（`src/channels/x.js`、`x-actions.js`、`douyin.js`），
所以她说「推特我这边打不开、抖音我也刷不了」在当时的**实际状态**下是真的，但根因是
**余额熔断 + 抖音未绑定 + 代理/登录态**，不是「项目没有这个功能」。充值或调阈值、绑定抖音、重配 Cookie 后，
这几项会直接回来。

### 4.2 功能在，但没接进 QQ 聊天（小改动可补）

`src/channels/onebot.js` 的 `parseOwnerCommand` 只有 10 条口令：状态、自动运营开/关、逛一下、发一条、
今天做了啥、发条语音、语音聊天开/关——**全部指向小红书、语音和状态**。

- X / 抖音 / QQ 空间的模块都在，但**控制台之外没有聊天内入口**，所以她在 QQ 里根本调不到，只能说「我这边没有」。
- 发图：`onebot.js` 已有 `sendStickerToTarget`（`base64://` 发图）和图片入站理解，但**没有「把任意图片/截图发给主人」的通道方法**。
- 截图：`src/browser/cdp.js` 有 `Page.captureScreenshot`，只给小红书/抖音的**浏览器页面**用；**没有桌面截图**。
  所以她说「没有能往外传图的工具」指的是这一层，不算说错。

### 4.3 确实没有，且不建议按「完全权限」补

| 她说做不到 | 现状 | 建议 |
| --- | --- | --- |
| 看自己的代码、改自己 | 模型只拿到人设、记忆、近期对话和真实回执；拿不到 `src/` | **保持**。让她自我改代码等于给任意代码执行 |
| 装脚本、点鼠标、敲键盘、开网页、动系统设置 | 没有桌面自动化工具层 | 要做得按她自己在聊天里说的办：「给我开几个明确的窗口，比开一整扇门靠谱」——白名单动作 + 每次二次确认 + 全程日志，不给完全权限 |
| 屏幕截图发给主人 | 见 4.2 | 可做，但涉及隐私，建议单独开关 + 只在主人私聊 + 截图前明确提示 |

## 五、建议的处理顺序

**P0（现在就能做，不用改代码）**
1. 充值，或在设置 →「界面与系统 / 费用」把 `lowBalanceCny` 调到合适值——这一条解开大半「她不做任何事」。
2. 设置 → 抖音 →「读取我的作品」完成账号绑定。
3. 重新登录 QQ 空间并复制完整 Cookie，清掉反复出现的失效告警。
4. 处理小红书的安全验证（人工，程序已按设计停 6 小时）。

**P1（小改动，逐个接上并补判据）**
5. QQ 通道增加「发任意图片 / 桌面截图」方法（默认关，主人私聊，带提示与日志）。
6. 把 X / 抖音 / 空间的只读能力接进 QQ 口令，让她能如实说「我去看一下」而不是一律说没有。
7. 给她一个「当前能力清单 + 为什么这次没做」的只读上下文：余额熔断、账号未绑定、Cookie 失效、平台风控要能说清楚原因，
   不然她只能笼统地说「我这边没有」，主人也无从下手。

**P2（要设计，别急）**
8. 桌面操作工具层：白名单 + 二次确认 + 审计日志，逐项开窗口，不做「完全权限」。

**不做**
9. 让她读/改自己的源码；给她整台机器的完全权限。
