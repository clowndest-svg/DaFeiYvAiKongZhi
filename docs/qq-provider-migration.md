# QQ 接入端迁移评估与操作方案

评估日期：2026-11-06。结论：具备替换条件后，可将 NapCat 替换为 SnowLuma；当前不满足生产切换门槛。采用可回退的单接入端方案，保留现有应用，不引入 AstrBot。可靠性机制已实现并进行隔离测试；实机交接采用维护模式，真实 QQ 验收与长期稳定性单独记录。

## 1. 为什么这样选

本产品已经拥有聊天、人设、记忆、心情、会话隔离、语音、图片学习、主动消息、预算和社交调度。再引入 AstrBot 会多出一套上下文、数据库、定时任务和回复决策，需要重新定义数据所有权，收益不足以覆盖重复回复、记忆分叉和额度重复计算的风险。

推荐链路：

```text
桌面 QQ 机器人小号
  ↕ 唯一启用的接入端（NapCat 或 SnowLuma）
OneBot v11 反向 WebSocket（校验令牌与机器人身份）
  ↕
现有 OneBotChannel
  ├─ 私聊/群聊/白名单/主人身份
  ├─ 消息去重、会话队列、取消旧回合
  ├─ 文本/图片/表情/语音收发
  ↕
现有 Companion / Scheduler / TTS / ASR
  ↕
现有唯一 SQLite 数据库、设置、人设、记忆与预算
```

SnowLuma 是否更稳定，需要同机、同 QQ 版本、同账号条件下实测，不能由评论或“保留图形界面”推出。软件稳定、QQ 登录状态、WebSocket 连接、模型服务和账号风控是不同问题。

## 2. 现有功能与依赖

| 功能 | 所属与依赖 | 迁移处理与验收 |
| --- | --- | --- |
| 主人私聊、共享记忆与人设 | Companion + 原 SQLite | 保留原 owner、botAccount、会话与数据库路径；不得重绑或新建第二套记忆 |
| 群聊、访客隔离 | OneBotChannel + 原 session 映射 | 测群白名单、@、群会话和访客隔离；不改变现有映射键 |
| 主动找你、自己接话 | 原 Scheduler / follow-up timers | 仍只由本应用调度，切换前须等现有回合与计时任务结束或明确取消 |
| 图片、普通表情、商城表情 | OneBot 消息段、URL、原素材库 | 分别验证 image/face/mface；mface、媒体 URL 和扩展字段不能只凭 OneBot 名称假定兼容 |
| 收语音、发语音、语音会话 | record/get_record + 本地 ASR/TTS | 验证接收音频格式、转换与上传、回执、额度、打断；这是语音消息会话，不代表原生 QQ 实时通话 |
| QQ 空间 | 原空间 Cookie + get_cookies/get_credentials 扩展 | 保留现有有效 Cookie；验证新端返回内容与账号归属。不兼容时保留本机手动 Cookie 路径，不伪造成功 |
| 小红书、X、心情、日报、预算 | 原应用调度与原 SQLite | 不搬迁，不另起任务；做回归确认 QQ 通道切换没有改变调度和额度 |
| 登录/扫码/进程监控 | 原来直接依赖 NapCat | SnowLuma 改为桌面 QQ 扫码、管理页手动接入小号进程；禁用旧端开机自愈与版本提示 |
| 升级/回退 | QQ 与协议端版本组合 | 固定通过验收的组合；不自动跟随 latest、不自动轮换协议端 |

## 3. 本次已落地的准备

- `BIZHI_QQ_PROVIDER` 启动时固定选择，默认 `napcat`，非法值直接报错。服务运行期间保存设置不会热切换接入端。
- NapCat 路径 `/onebot`；SnowLuma 路径 `/onebot/snowluma`。同一服务器只接受所选路径，防止旧端自动回连混入新端事件。
- 每次只接收一个 WebSocket；第二条连接拒绝，旧连接关闭后方可连接。
- 启动入口同时使用进程内互斥和本项目数据目录中的独占文件锁，阻止控制台与启动脚本同时发起启动。启动操作异常退出留下锁时不自动强行清锁，须确认没有在途启动后人工处理。
- 收到的账号身份不匹配时关闭连接，不覆盖已有正确账号身份；消息必须为数组格式并带有效 self_id。
- 同一 SQLite 中增加回执、入站队列、出站台账及费用预留表；显式设置 WAL + synchronous=FULL。去重包含账号、会话、群、发送者、消息 ID 与规范化时间；ID 0 合法。回执至少保留 24 小时，完成记录在启动时按 7 天窗口清理；未解决记录不清理。
- 发送超时、连接关闭、服务关闭、底层写入错误保留 `DELIVERY_UNKNOWN`，不把可能已经发出的消息当成明确失败后自动重发。
- 所有启动脚本经统一协议端入口分派；SnowLuma 进程所有权同时检查本项目完整路径、入口与内置 Node，禁止误杀其他 Node。
- SnowLuma 必须关闭自动注入，仅绑定本机 WebUI；全局 OneBot 默认不连接任何账号，仅机器人账号配置反向 WS；不打开额外 HTTP/WS 监听。
- SnowLuma 首次启动要求 QQ 进程确认全部不存在，不代关主号；这能避免已载入 NapCat 的孤儿 QQ 进程被第二次注入。实例查询失败时不继续。
- 设置页从接口读取当前端、地址与登录说明；SnowLuma 不展示 NapCat 缓存二维码，不读 NapCat 旧日志诊断其登录，不运行 NapCat 开机自愈/升级检查。
- 停用提示不再声称桌面 QQ 已退出。NapCat 的启动器注入后可能已退出，停止启动器不能证明孤儿 QQ 已关闭。
- 状态接口暴露 `status.migration` 的队列、发送中、回复中、语音会话数量。`idle` 只是当时观测，并非全局迁移锁。

## 4. 一致性边界，必须明确

外部 QQ 发送和本机 SQLite 没有分布式事务，OneBot v11 也没有本产品可依赖的统一幂等发送键。不能承诺跨故障“恰好发送一次”。本次选择发送结果不确定时停止自动重发，避免双发。

原始入站事件与去重回执在同一事务落盘。状态为 received → dispatching → buffered → processing → completed，异常进入 review。重启时仅同账号、同主人、同协议端且未过期的 received/buffered 自动恢复；dispatching/processing 一律进入人工核对，不盲目重跑模型或空间等外部副作用。原始事件保留在本机 SQLite，控制台列表不返回正文或媒体凭据。

出站每个分段在真正调用协议端前先写 sending；入站批次 + 分段序号 + 动作构成稳定键，已有已确认回执可复用，未知或已尝试的分段不自动重发。断线、超时、服务关闭或底层写入异常转 unknown，启动遗留 sending 同样转 unknown。人工核对只记结论，不补发。

QQ 回复在会话里记录 pending/sent/unknown/failed；正文确认送达后才触发该回合的记忆反思与摘要维护，未确认的旧回复在模型上下文中带明确说明。已收到的用户消息不因回复未知而丢掉。

这些机制保留可核对证据，不能替代上游离线补推，也不能证明所有硬件断电场景下零丢失。平台收到但尚未入队的消息、失效媒体 URL 和跨端变动的消息 ID 仍需要原 QQ 窗口对账。本地已做子进程终止故障注入，未做整机断电测试。

不同协议端可能为同一条 QQ 消息产生不同 message_id。本次去重不能保证跨端历史重放仍去重。因此必须冷交接，不允许两个端同时消费，不允许迁移时自动导入历史，不能按“文字相同”合并用户连续发出的相同消息。对切换窗口内收件使用 QQ 原窗口对账。

QQ 原生进程身份不一定能从 `-q` 参数可靠识别。SnowLuma 的桌面模式下，原有同账号实例探测只能作为辅助信息，不能据此杀进程。自动发现的 QQ 主号也不能直接注入，即使应用层最终会拒绝其消息。

回退只恢复协议端配置和启动选择。切换后已产生的新聊天、记忆、预算、社交记录仍使用同一个数据库。禁止用迁移前数据库覆盖运行中的数据库，否则会丢新数据并可能重复执行外部动作。

## 4.1 费用、维护与数据所有权

每次真实模型请求在发出前按当前定价估算预留费用；返回 usage 后，预留结算与 costs 写入处于同一事务，同一预留不能重复结算。网络故障、5xx 或进程中断保留未知预留；明确的 4xx 拒绝释放预留。日预算同时计入未结算预留，不通过重启归零。时区仍沿用现有 UTC+8 日界，与 Asia/Taipei 当前日界一致，不另建第二套账。

预留是本地估计，使用既有可配置费率，不是服务商账单或保证上界。未知费用从平台账单核对后可在维护面板填实际金额；操作只结算，不重跑模型。账单尚未核实就不宣称费用零偏差。

维护标记持久保存：新入站事件继续落库，新主动消息、自接话及自动调度暂停，新写 API 返回 503，语音会话结束；已有文字回复继续排空。界面和状态接口同时观察 QQ 在途任务、网页聊天、反思/摘要及社交调度忙碌状态。人工核对、能力只读检查、结束维护仍可使用。未完成或未知记录始终可见；观察到排空不是对外部 QQ 服务的事务锁。

同一业务数据目录增加独占运行锁，避免另一端口上的第二个应用消费同一库。仅在旧 PID 确认不存在时恢复遗留锁，查询不可信或锁损坏时拒绝重复启动。回退仅更改接入端，继续使用这版兼容代码和当前数据库，不检出会忽略新台账的旧源码运行。

媒体只保存原始引用，不无条件下载未知私聊资源。恢复时若引用失效，沿用实际读取失败的降级提示，不编造看到了图片或听到了语音。空间仍走原 Cookie 验证和原副作用幂等规则；扩展接口状态与账号、接入端绑定，明确不支持时抑制自动导入重试，手动操作可重新核验。

## 6. 实机验收与切换顺序

以下为完整验收流程，部分交接步骤已执行；实际通过范围以第 8 节及任务记录为准。

1. 先在隔离 Windows 用户/虚拟机或独立测试账号、独立数据目录与端口中验证 SnowLuma。不得让它读写生产库或让测试消息触发生产社交任务。固定实际 QQ 版本与官方二进制哈希。
2. 操作者阅读并确认 SnowLuma 自身条款和隐私政策；本项目不预设 `SNOWLUMA_ACCEPT_EULA` 或 `SNOWLUMA_ACCEPT_PRIVACY`。
3. 确认候选配置关闭全局/非机器人账号适配器、关闭自动注入、WebUI 仅本机，所有已有账号覆盖配置都要检查，不能只检查全局配置。
4. 验证文字双向收发、连续同文、离线重连、重放去重、错误账号、第二连接、超时与断网、服务重启、群聊隔离、媒体与空间扩展。每种发送均核对 QQ 实际显示和本地记录，不能只看 WebSocket 已连接。
5. 功能通过后安排短维护窗口：停止用户输入，暂停主动消息/自接话/语音会话等新任务，等待 `migration.idle`，再核对没有其他正在运行的本应用实例。仅队列瞬时为零不足以形成并发锁。
6. 再做快照，记录交接时间与最后确认消息。停止旧协议端及旧服务，手动确认旧机器人 QQ 已退出、没有后台旧实例。不要通过全局 taskkill 杀所有 QQ。
7. 将启动配置改为 `BIZHI_QQ_PROVIDER=snowluma`，保持原数据库、设置、owner、botAccount、令牌及素材目录。此时才把已验证的配置装入 SnowLuma。
8. 启动本应用和 SnowLuma；确认没有运行 QQ 后再打开桌面 QQ，用机器人小号扫码，在 SnowLuma 手动选择该进程接入。`-q` 参数不能证明 QQ 最终登录了该账号，必须由操作者核对 QQ 界面实际账号及对应进程；若主号和小号无法明确区分，不注入。不得仅凭参数结束或加载 QQ。
9. 确认只有一条反向连接、登录身份正确、账号 online、文字入站与出站均通过，再逐项恢复主动消息、语音、表情与空间任务。
10. 先观察 24 小时，再观察 72 小时。记录真实断连次数/时长、入站、出站确认、未知发送、重复消息、漏处理和人工登录次数。观察不足或仍有未解释的故障，不标注“长期稳定”。

## 7. 回退

发生错号、重复回复、媒体关键能力失败、漏处理或无法解释的反复断连时停止迁移。

停止产生新回复并核实当前在途发送，停 SnowLuma；手动确认机器人 QQ 未残留其 Hook。恢复 `BIZHI_QQ_PROVIDER=napcat`，以原配置启动旧端与应用，使用当前数据库。按交接时间对账，不自动补发结果未知的消息。若只是接入失败，不恢复数据库快照；快照只用于独立数据损坏事故的恢复评估。

## 9. 操作接口与验收矩阵

`GET /api/qq/setup` 提供接入端、账号健康、能力状态及维护/排空观察；`POST /api/qq/maintenance` 的布尔 enabled 控制维护。`GET /api/qq/journal` 提供不含消息正文的待核对列表，`POST /api/qq/journal/resolve` 只记录人工结论。费用核对另需 actualCostCny，并与费用结算同事务。接口沿用控制台鉴权、来源校验与动作锁。

`POST /api/qq/capabilities/check` 只调用基础只读能力；接口应答与真实收发分开标记。维护面板可以看到待处理、回复中、未知发送、其他后台业务与费用待核对；维护期间的新写入 API 返回 503，不能靠另开页面绕过。
